第 02 章

基线：逐词线性层与小 MLP

最简单的 head 就是每个词一个线性分类器。它回答一个最基本的问题：冻结 LiLT 的特征本身，已经能把字段分开到什么程度。后面每一类更复杂的 head，增益都要相对这条基线、在同一设置下算。

对应脚本 code/ch02_linear_mlp.py head 定义 code/heads.py

§1同一个线性 head，四种输出契约

HF 的 LiltForTokenClassification 只用文本流最后一层（768 维）接 Dropout + Linear。官方仓库的 LiLTRobertaLikeForTokenClassification 先把文本流和 layout 流拼起来（768 + 192 = 960 维），再接一个 Linear。代码 两份实现都没有 MLP，也没有 CRF。这两种接法，加上“只用 layout 流”和“文本流最后 4 层 + layout 流”，用同一个线性 head 各跑 3 个种子：

python ch02_linear_mlp.py · §1FUNSD · 冻结 LiLT
  linear · text 768          宏F1 0.657±0.001  Q 0.730  A 0.734  H 0.506  实体全对 0.731  ECE 0.018
  linear · layout 192        宏F1 0.594±0.002  Q 0.583  A 0.640  H 0.560  实体全对 0.579  ECE 0.016
  linear · both 960          宏F1 0.679±0.005  Q 0.731  A 0.748  H 0.558  实体全对 0.712  ECE 0.011
  linear · last4 3264        宏F1 0.691±0.006  Q 0.750  A 0.764  H 0.560  实体全对 0.757  ECE 0.034
  Q/A/H = question/answer/header 的逐词 F1；宏F1 = 三者平均；实体全对 = 实体里每个词都标对的比例。

线性 head 的宏 F1：四种输出契约

误差线是 3 个种子的标准差；橙色是本课默认的 both 960。横轴从 0.5 开始。悬停看传输量。

  • 只用 HF 默认的 768 维，比 960 维低 2.2 个点，header 低得最多（0.506 vs 0.558）。192 维的 layout 输出在冻结设置下有用，丢掉可惜。本课实测
  • 只用 layout 流也有 0.594，header F1（0.560）甚至高于只用文本流。表单里“标题在哪儿”很大程度上是个位置问题。
  • last4 再高 1.2 个点，代价是每个词传 3264 维，是 960 维的 3.4 倍。值不值，要看你的传输和存储预算。

§2线性 vs 小 MLP

python ch02_linear_mlp.py · §2FUNSD · 冻结 LiLT
  linear · both 960          宏F1 0.679±0.005  Q 0.731  A 0.748  H 0.558  实体全对 0.712  ECE 0.011
  MLP · both 960→256→4       宏F1 0.690±0.003  Q 0.730  A 0.755  H 0.584  实体全对 0.708  ECE 0.159

MLP 的宏 F1 高 1.1 个点，主要涨在 header 上。但是 ECE 从 0.011 涨到 0.159，置信度变得很不可靠（§3 解释 ECE）。参数也从 3,844 涨到 247,044。还有一点要留心：论文 Hewitt 和 Liang（2019）指出，表达能力更强的探针自己就能拟合出一部分结果，准确率涨了，不一定说明特征里多了信息。MLP 的这 1 个点里，有多少来自 head 的容量，这组实验分不出来。

§3置信度：softmax 最大值靠不靠谱

输出契约里要的“模型置信度”，对线性 head 来说就是 softmax 的最大概率。它准不准，可以按置信度分段来看：每段里的词，平均置信度和实际准确率差多少。ECE 就是这些差值按词数加权求和：

ECE = Σm (|Bm| / n) · | acc(Bm) − conf(Bm) |
python ch02_linear_mlp.py · §3FUNSD · 冻结 LiLT
  置信度 (0.00, 0.50]   1322 个词  平均置信度 0.437  实际准确率 0.445
  置信度 (0.50, 0.70]   2664 个词  平均置信度 0.597  实际准确率 0.587
  置信度 (0.70, 0.90]   3072 个词  平均置信度 0.806  实际准确率 0.785
  置信度 (0.90, 0.97]   1306 个词  平均置信度 0.935  实际准确率 0.938
  置信度 (0.97, 1.00]    343 个词  平均置信度 0.982  实际准确率 0.983
  ECE = 0.013（越接近 0 越可信）

线性 head 的可靠性图（测试集，种子 2）

每个点是一个置信度区间：横轴是平均置信度，纵轴是实际准确率。落在虚线上 = 说多少就是多少。

线性 head 几乎贴着对角线，ECE 0.013：它说 0.8，大约就是 80% 的对。这对下游很重要，比如“置信度低于 0.7 的送人工复核”，这条规则只有在置信度可信时才成立。后面会看到，更复杂的 head 往往把这个性质弄丢了。另外，这是在 FUNSD 测试集上的结论。换了数据分布，校准也可能变，上线前要在自己的验证集上重新看。

§4错在哪里

python ch02_linear_mlp.py · §4FUNSD · 冻结 LiLT
                 other  question    answer    header
  other           1520       270       533        62
  question         339      1879       365        71
  answer           496       253      2530        15
  header            39        84        56       195

每行按真值归一化：对角线是召回率，其余是被错标成哪一类。

最大的两块错误都在 other 和 answer 之间：533 个 other 被标成 answer，496 个 answer 被标成 other。再往下是 question 被标成 answer（365 个）或 other（339 个）。一个 answer 长什么样，很大程度上取决于它旁边是不是一个 question。每个词单独分类时，这份上下文只能靠 LiLT 特征里已经带的那部分。第 3 章就测“在 head 里再看一眼邻居”能补回多少。

§5成本

  linear · both 960      参数     3,844   文件     16.8 KB
  linear · last4 3264    参数    13,060   文件     52.8 KB
  MLP · both             参数   247,044   文件    967.3 KB
  linear · text 768      n=64:   0.02  n=128:   0.03  n=256:   0.04  n=512:   0.07   (p50, ms)
  linear · both 960      n=64:   0.02  n=128:   0.03  n=256:   0.04  n=512:   0.07   (p50, ms)
  linear · last4 3264    n=64:   0.04  n=128:   0.06  n=256:   0.11  n=512:   0.25   (p50, ms)
  MLP · both             n=64:   0.09  n=128:   0.14  n=256:   0.25  n=512:   0.46   (p50, ms)

线性 head 是 16.8 KB 的文件，一份 256 词的文档 0.04 ms。backbone 单线程一次前向要 392 ms，head 大约是它的万分之一。即便是 MLP，0.25 ms 也微不足道。这一档 head 的延迟可以不算，要算的是准确率和置信度。

要点

  1. FUNSD 上，冻结 LiLT + 线性 head 的逐词宏 F1 是 0.679。这是后面所有 head 的对照基线。
  2. 输出契约有影响：只用 HF 默认的 768 维低 2.2 个点。我建议 backbone 服务吐 960 维（文本 + layout）。
  3. MLP 只多 1 个点，ECE 却从 0.011 变成 0.159。要用它的置信度，得先做校准。
  4. 线性 head 的成本可以忽略（3,844 个参数，0.04 ms）。剩下的主要错误是 other 和 answer 互混，这要看上下文。
