第 00 章

问题与证据规则

这门课接着 LiLT 架构课第 7 章往下讲。LiLT 冻结以后，所有任务共用它算出的特征，每个任务只训练自己的 head。这个 head 用什么结构，是本课要回答的问题。动手之前，先讲清楚两件事：问题的边界在哪里，什么样的数字才算回答了它。

本章没有配套脚本 实验从 第 1 章开始

§1要解决的问题

  • 输入：OCR 给出每个词的文字和位置框。
  • 输出：每个词属于哪个字段，比如姓名、日期、金额。不属于任何目标字段的词归为 Other。标签是扁平的，只有字段名，没有 B- / I- 前缀。每个词还要附带一个模型置信度。
  • 任务很多：不同文档类型、不同业务方要抽的字段集合不同。设想有几十个这样的任务组合（架构课第 7 章用 60 个举例）。一个任务可以同时抽好几个字段。任务数也不等于要部署的服务数。
  • 在 CPU 上推理：单份文档的延迟、常驻内存、所有任务的模型文件总量都要算进成本。
两件事别混在一起

LoRA 是低秩增量，参数通常远少于 backbone，不能不量就说它“大”。换方案的理由主要是另一点：加了 LoRA 的特征只属于那一个任务，别的任务没法复用同一次前向。另外，“backbone 和 head 拆成两段”是设计上的分层，不等于一定要部署两个、或者 T+1 个服务。

§2输出契约：backbone 和 head 之间传什么

head 能用什么结构，取决于 backbone 服务吐出什么。下面几项一旦定下来，所有任务的 head 都按它训练；以后要改，所有 head 都得重训。

项目选项本课怎么做
哪条流、哪几层文本流最后一层 768（HF 默认）· 再拼 layout 流 192 = 960（官方任务头）· 最后 4 层 3264默认 960；第 2 章比较这四种
粒度subword 级，还是词级每个词取第一个 subword 的向量，head 看到的是词序列
掩码与词映射哪些位置是真实的词、subword 属于哪个词必须随特征一起给
长文档LiLT 一次最多 512 个 token按 token 数切成不重叠的窗口（第 1 章）
词框只有显式用版面的 head 要第 5 章的版面 head 用
输出每个词的预测 + 模型置信度置信度怎么定义随 head 而变（softmax、CRF 边际、片段分数、投票比例）
模型置信度不是 OCR 置信度

OCR 表里常有一列 conf，那是识别字符的把握。head 输出的是“这个词属于这个字段”的把握。两者含义不同，不能互相顶替，也不能直接相乘当成总置信度。最后交给下游的列名要单独约定，比如 predict 加 prob。

§4证据规则：什么样的数字能回答这个问题

文献里关于这些 head 的数字不少，但大多回答的不是我们的问题。按和目标设置的距离，从近到远排：

  1. 同设置的直接证据：冻结 LiLT，用同一份数据切分、同一套扁平标签，在同一类 CPU 上测。文献 2026-11 检索时一条也没找到，包括在 FUNSD、CORD、SROIE 上给冻结的 LayoutLM 系列、LiLT、BROS 接线性或小 probe 的工作。检索没命中，不等于一定不存在。
  2. 其他冻结编码器的证据：论文 BERT 论文 §5.3：冻结 BERT-base，拼接最后 4 层，接两层 768 维 BiLSTM，CoNLL-2003 dev F1 96.1；整体微调是 96.4。Peters 等（2019）：冻结 BERT-base，对各层加权求和后接两层 BiLSTM，CoNLL-2003 test F1 92.2；微调是 92.4。这两条都是纯文本的新闻 NER，而且用的 head 不轻。
  3. 端到端微调的结果：论文 LiLT 在 FUNSD 上的 F1 0.8841，是整个模型一起微调、用 BIO 标签、按实体级算出来的。官方训练脚本里也找不到任何冻结逻辑。这个数不能拿来当冻结 head 的基线，也推不出两种设置差多少。
  4. 只靠结构推断：推断 复杂度公式、参数量、“LiLT 已经有全局注意力，再加一层可能冗余”这类论证。它们能说明可能怎样，说明不了实际会怎样。

本课补上的是第 1 级风格的实测：本课实测 用同一个冻结的 LiLT checkpoint、同一份切分、同一套扁平标签、同一台 CPU，把八类 head 放进同一张表。它回答的是在 FUNSD 上的问题，换成你自己的文档，结论要重新量。

§5FUNSD 实验和目标场景：哪里一样，哪里不一样

一样的
  • 冻结的 SCUT-DLVCLab/lilt-roberta-en-base，一个参数都不更新
  • 词级扁平标签加 other，没有 BIO
  • 词框来自标注，按几何位置排出类似 OCR 的阅读顺序
  • CPU 推理，单线程、batch=1 计时
不一样的
  • FUNSD 是 199 份英文扫描表单，只有一个任务
  • 标签是 question / answer / header 这类语义角色，不是业务字段
  • 训练集 119 份，比真实任务可能少得多，也可能多
  • CPU 是 Apple M1，不是目标机型；不含序列化和网络

要点

  1. 问题：冻结 LiLT 作为共享 backbone 时，每个任务的 head 选什么结构，才能在准确率、CPU 成本和多任务维护之间取得平衡。
  2. 先定输出契约（哪几层、粒度、掩码、长文档、词框），head 的可选范围由它决定。
  3. 文献里没有同设置的直接证据。论文数字只能代表它们自己的设置，不能当本项目的预测。
  4. 本课在 FUNSD 上做受控对照，并给出每种 head 的大小和延迟。它是第一手数据，但只代表 FUNSD。
