第 07 章

落地：冻结 backbone + 轻量 head

前六章讲的是 LiLT 本身。这一章讲一种落地方式：把 LiLT 冻结成所有任务共享的特征抽取器，每个任务只训练一个轻量的 head。要定下来的是三件事：backbone 吐出什么特征、head 怎么训、成本落在哪里。

对应脚本 code/ch07_frozen_backbone.py 运行 python ch07_frozen_backbone.py

§1特征抽取器：backbone 到底吐出什么

脚本里的 FrozenLiLTFeatures 把 “words + 像素框” 变成 “每个词一个向量”。它有三个旋钮，这三个旋钮就是 backbone 服务的输出契约，定了以后所有 head 都按它训练，改了就要全部重训：

旋钮选项说明
streamstext 768 · layout 192 · both 960只用 HF 的 last_hidden_state 就等于 text，192 维的 layout 输出被丢掉（第 6 章）
layers默认 (11,)；也可以 (8, 9, 10, 11) 取平均冻结特征时，多层平均有时比只用最后一层稳；要实测
poolingfirst · mean一个词多个 subword 时取第一个，还是取平均
 
class FrozenLiLTFeatures:
    def __init__(self, model, tok, streams="both", layers=(11,), pooling="first"):
        ...
    def __call__(self, words, boxes_px, page_w=PAGE_W, page_h=PAGE_H):
        boxes = [normalize_box(b, page_w, page_h) for b in boxes_px]
        enc = encode(self.tok, words, boxes)
        taps = run_with_taps(self.model, enc)          # 一次前向，两条流每层都取出来
        parts = []
        if self.streams in ("text", "both"):
            parts.append(torch.stack([taps["text"][k] for k in self.layers]).mean(0))
        if self.streams in ("layout", "both"):
            parts.append(torch.stack([taps["layout"][k] for k in self.layers]).mean(0))
        tok_feats = torch.cat(parts, -1)[0]            # [L, D]
        ...                                            # 按 word_ids 池化成 [W, D]

超过 512 个 token 的文档

LiLT 的最大长度是 512。超出的部分会被截断，被截掉的词在 word_feats 里是全零向量，head 照样会给它们一个预测。生产环境要按窗口切分（比如带重叠的滑动窗口），再把每个词的特征从它所在的窗口里取回来。

§2冻结 backbone + 线性 head 的训练流程

流程只有两步：特征算一次存起来，head 在特征上反复训练。backbone 的参数全部 requires_grad_(False)。

FIELDS = ["Other", "invoice_no", "date", "name", "address", "total"]
X = fx(doc["words"], doc["boxes_px"])["word_feats"]           # [W, 960]，算一次就可以反复用
y = torch.tensor([FIELDS.index(f) for f in doc["field"]])
head = torch.nn.Linear(X.shape[1], len(FIELDS))
opt = torch.optim.AdamW(head.parameters(), lr=1e-2)
for step in range(200):
    loss = torch.nn.functional.cross_entropy(head(X), y)
    opt.zero_grad(); loss.backward(); opt.step()

训练集只有一张文档，全对、prob 全是 1.00 只说明过拟合了，这里只看流程。还有两点要注意：

  • prob 不是 OCR 的置信度：head 输出的 prob 是模型对字段归属的把握，OCR 的 conf 是对字符识别的把握，两者不能混用，也不能相乘当成“总置信度”而不做校准。
  • 冻结有代价：论文的数字都是整个模型一起微调得到的。冻结 backbone、只训线性 head，效果一般会低一些，换来的是第 3 节的成本优势。差多少要在自己的数据上量，这是工程判断，不是论文结论。

§3CPU 计时：一次 backbone 前向 vs 60 个线性 head

序列长度 512、4 线程，在本机 CPU 上实测（脚本运行于 2026-11-17）：

backbone 一次前向
290.9 ms
512 token，冻结的 LiLT
60 个线性 head 合计
3.28 ms
平均每个约 0.055 ms
backbone 98.9%

橙色细条是 60 个 head 的 1.1%。具体毫秒数随机器变化，比例才是重点。

成本几乎全在 backbone。60 个任务如果各自微调一个 LiLT，就要跑 60 次前向、存 60 份完整权重（官方 en-base checkpoint 一份就是 293 MB）；共享一次前向、按任务换 head，前向只跑一次，每个 head 只有几千个参数。这是这个方案省钱的根本原因。

§4如果要缓存特征：每份文档多大

特征fp32fp16
512 token × 768 维（text）1.57 MB0.79 MB
512 token × 960 维（both）1.97 MB0.98 MB

按 token 存最灵活（以后能换 pooling），按词存更小（词数 W 比 token 数少，示例发票是 32 个词对 66 个 token）。存了缓存，新增一个任务时只需要在缓存上训练新 head，不用再跑 backbone。代价是：输出契约（§1 的三个旋钮）一旦改了，缓存全部作废。

要点

  1. 落地方式：冻结 LiLT，一次前向得到词特征，每个任务一个轻量 head。
  2. 先定输出契约：哪条流、哪几层、怎么池化。我倾向 both 960 维，和论文的原版任务头一致；只用 HF 的 768 维会丢掉 layout 输出。
  3. 成本几乎全在 backbone（本机 291 ms vs 60 个 head 共 3.3 ms），共享前向是省钱的关键。
  4. 超过 512 token 要切窗口；head 的 prob 不是 OCR conf；冻结比整体微调效果低多少要实测。
